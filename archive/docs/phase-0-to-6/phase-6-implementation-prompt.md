## このPhaseの目的

毎週、Steamを中心に、予算とやまもとの好みに合う未所有ゲームを3本選び、根拠と基本情報を確認できる形で提案する仕組みを作る。

このPhaseでいう「採用」は、次週に扱うゲーム候補を内部的に決めることだけを意味する。ゲームの購入、Steamウィッシュリストの変更、記事の公開、SNS投稿を自動で行ってはならない。

## 実装前に確定する事項

以下は調査結果と推奨案を示し、ユーザーの回答を得てから外部設定や本実装へ進む。

### 1. Steamライブラリの取得方法

現在利用できるSteam公式資料を確認し、少なくとも次を比較する。

- Steam公式APIを使う方法
- ユーザーがCSVまたはJSONを手動で用意する方法
- 初期版は手動ファイル、後から公式APIへ切り替える方法

非公開API、ログイン済みページのスクレイピング、Cookieの取得・保存、パスワード入力の自動化は採用しない。Steamプロフィールやゲーム情報の公開設定を変更する必要がある場合、プログラム側で変更せず、公開範囲とプライバシー上の影響を説明してユーザー自身に判断してもらう。

### 2. Steamウィッシュリストの取得方法

安定した公式取得手段があるかを最新の公式情報で確認する。公式手段がない、または不安定な場合は、手動エクスポートや手入力ファイルを第一候補とし、非公式エンドポイントへ暗黙に依存しない。

### 3. 月間購入額の入力元

通常予算は月15,000円、特に注目すべき作品がある月だけ最大30,000円である。ただし30,000円枠はユーザーの月ごとの明示承認なしに有効化しない。

Steam購入履歴をスクレイピングしない。初期版は、購入日、App ID、作品名、支払額だけをユーザーがローカルの非公開データへ入力する方式を推奨する。保存場所、Git管理対象外の設定、Obsidianとの役割分担をユーザーと確定する。

### 4. 候補発見と事実確認の方法

Phase 5のGemini調査処理を再利用できるか確認する。ただしPhase 5の実運用は保留中であり、Phase 6をPhase 5の記事生成・公開へ結合しない。

AIを使う場合は「候補と出典の収集、理由文の下書き」に限定する。App ID、所有状態、価格、対象地域、評価、日本語対応、成人向け・残虐表現、予算判定などの制約は、プログラムが検証済み構造化データから決定する。AIの自己申告だけで事実を確定しない。

### 5. 月曜24時の未選択時処理

既存仕様は「第1候補を採用」だが、初期実装では次の意味に限定する。

- 内部の選定結果へ `auto_selected_rank_1` として記録する
- Discordへ未選択だったことを通知する
- ゲームを購入しない
- Steamライブラリやウィッシュリストを変更しない
- 記事を生成、同期、公開しない
- SNSへ投稿しない

この挙動を有効化するか、当面は注意通知だけにするかをユーザーへ確認する。明示承認前の初期値は「注意通知だけ」とする。

## 基本設計

### 処理を4段階に分離する

1. **入力と候補収集**  
   ライブラリ、ウィッシュリスト、購入台帳、候補と公式出典を読み込む。
2. **適格性検査**  
   所有済み、予算超過、成人向け、強い残虐表現、必須情報不足を除外する。
3. **決定的な採点と上位3本の提示**  
   設定値と検証済み事実から再現可能な点数を計算する。
4. **人による選択と履歴保存**  
   Obsidianの選択結果を安全に読み、選定結果と後日の記事結果を学習用履歴へ保存する。

各段階を独立してテストできるようにし、外部取得に失敗しても既存データや完成済み成果物を壊さない。

### 適格性検査を採点より先に行う

次は点数ではなく除外条件として扱う。

- 所有済み作品
- 通常予算または承認済み上限を超える作品
- 成人向け作品
- 強い残虐表現を中心とする作品
- App IDや一次情報など、判定に必要な情報が不足する作品
- 地域または通貨が対象外で、円価格を安全に確定できない作品

一般的な戦闘、ホラー、軽度の流血表現は自動除外しない。成人向け・残虐表現の判定が曖昧な作品は安全側で候補から外し、理由を要確認として残す。

### 採点

`strategy.yaml` の優先順位を読み込み、少なくとも次を項目別に採点する。

- 発売直後などの話題性
- 検索需要
- やまもとの好みとの一致
- 他ブログの競合状況
- Steam評価
- 価格の安さと残予算への収まり
- 日本語対応
- 週次記事への適性
- 月次エッセイへ発展できる可能性

重み、点数範囲、欠損値の扱いを設定として明示する。同じ入力なら同じ順位になる決定的処理とし、同点時の規則も固定する。検索需要、話題性、競合状況に信頼できる取得元がない場合、数字を捏造せず「不明」として扱う。AIに最終点数や除外条件を書き換えさせない。

好みのジャンルや参考作品は加点材料であり、対象ジャンルを固定する条件ではない。STGやテンポの悪さは避ける傾向として扱うが、根拠が曖昧な場合は断定しない。

### 候補3本の出力

各候補へ、少なくとも次を表示する。

- 順位
- ゲーム名とApp ID
- Steam公式URL
- 選定理由
- 価格と残予算
- 日本語対応
- Steam評価
- 検索・話題性（5段階。不明の場合は不明）
- やまもと適合度（5段階）
- 項目別の点数と総合点
- 所有・ウィッシュリスト状態
- 成人向け・残虐表現の確認結果
- 情報源と確認日時
- 早期アクセス等の注意事項

有効候補が3本未満なら架空候補や条件違反の作品で補わず、実在確認できた本数だけ表示して注意通知を出す。

AIが理由文を生成する場合、検証済み事実と短い編集上の文脈だけを渡す。Steamライブラリ全体、購入履歴全体、個人メモ、秘密情報をAIへ送らない。AI応答は許可した文章欄だけを更新できるようにし、事実項目を変更した場合は不採用とする。

## 通知と選択

### 月曜6時5分の通知

`Asia/Tokyo` の月曜6時5分に `今週の指示` へ候補3本を通知する設計とする。

- 初期実装は手動実行とfake通知で検証する
- 実Discord送信とschedule有効化は、それぞれ個別にユーザー承認を得る
- Discord Webhook URLはSecretで管理し、表示、保存、commit、ログ出力しない
- Discordにはライブラリ一覧、購入履歴、個人情報を載せない
- メンションを無効化する
- 同じ週の重複送信を防ぐ
- 通知失敗で候補データや既存成果物を壊さない
- Phase 5の日曜18時workflowと成果物名、Secret名、排他制御を衝突させない

### Obsidianの選択結果

Obsidian原稿や個人メモを広く走査しない。ユーザーと合意した専用ファイル1件だけを、固定スキーマと許可されたパスで読み込む。

選択入力には少なくとも週ID、選択したApp ID、選択日時を持たせる。候補外App ID、別週、複数選択、形式不正、期限後の競合、ファイルのすり替わりを検出する。Phase 6からObsidian本文、画像、個人メモを変更しない。

## 履歴と改善

Git管理可能な非個人データと、非公開にすべきデータを分離する。履歴へ必要最小限として次を保存する。

- 週ID
- 候補App IDと順位
- 項目別点数、総合点、除外理由
- 人が選んだ候補、または未選択
- 自動仮採用の有無
- 記事化、繰越、見送りの結果
- 情報確認日時と入力データのハッシュ

Steamライブラリ全体、ウィッシュリスト全体、詳細な購入履歴は履歴へ複製しない。同じ作品の過度な再提案を防げるようにする。

「同じ不適合傾向が続いた」ことを、少なくとも理由分類と連続回数で検知できるようにする。基準を自動変更せず、四半期会議用の調整案として人に提示する。

## 安全策

- Steam、Discord、Google、GitHub等の認証情報を表示、保存、commit、通知しない
- Steamプロフィールの公開設定を自動変更しない
- ログイン済みSteamページや購入履歴をスクレイピングしない
- ゲームを購入しない
- ウィッシュリストへ追加・削除しない
- AI出力や外部入力をコマンドとして実行しない
- AIに所有判定、禁止条件、予算判定、最終点数を委ねない
- `review-report.md` を同期、commit、公開対象に含めない
- Obsidian原稿、画像、個人メモを変更、移動、削除しない
- 独立した `my-blog`、PaperMod submodule、Phase 4のバックアップを変更しない
- 記事を自動公開せず、SNS投稿も行わない
- Phase 7以降を先行実装しない
- 実サービスを使うテストを作らず、fakeまたはstubを使う
- 失敗途中の成果物を完成状態として残さず、一時ファイルと原子的置換を使う

## テスト要件

既存テストを後退させず、少なくとも次を自動テストする。

- 所有済み作品が必ず除外される
- App IDとURLの重複が除外される
- 通常予算15,000円と月間購入額から残予算を正しく計算する
- 明示承認なしに30,000円枠を使わない
- 予算超過作品が除外される
- 成人向け・強い残虐表現の作品が除外される
- 一般戦闘、ホラー、軽度流血だけでは自動除外されない
- 不明な禁止条件を安全側で止める
- 候補不足時に架空候補で3本へ補完しない
- 同じ入力で点数と順位が変わらない
- 同点時の順位規則が一定である
- AIが事実や点数を変えた応答を拒否する
- 候補理由にプレイ経験を捏造しない
- AI入力にライブラリ全体、購入履歴全体、Secret、個人メモが入らない
- Discord本文に秘密情報、個人情報、全ライブラリ、購入履歴が入らない
- メンションを無効化する
- 同じ週のDiscord重複通知を防ぐ
- Obsidianの許可外パス、別週、候補外App ID、形式不正を拒否する
- 未選択処理が購入、記事生成、公開、SNS投稿を行わない
- 外部取得、AI、Discord、保存の失敗時に既存成果物を壊さない
- Phase 5 workflowと成果物が衝突しない
- テストからSteam、Gemini、Discord等の実サービスを呼ばない

変更後に次を実施する。

1. Phase 6の単体・結合テスト
2. 既存の全回帰テスト
3. Python等の構文検査
4. Hugo本番相当ビルド
5. Git差分、秘密情報、意図しない `draft: false`、対象外ファイル、submodule差分の確認

## 段階的な実施順

### Step 1: 調査と設計

Steamライブラリ、ウィッシュリスト、購入台帳、候補発見、Obsidian選択の方式を比較し、推奨案、費用、プライバシー、保守負担、制約をユーザーへ説明する。この段階では外部設定を変更しない。

### Step 2: ローカル実装

ユーザーが承認した入力方式について、fakeデータによる入力、適格性検査、採点、候補3本、選択、履歴、通知dry-runを実装する。

### Step 3: ローカル検証

fakeデータで候補提示から選択・未選択までを通し、全テストとHugoビルドを成功させる。成果物を人が読める形で提示する。

### Step 4: 外部接続

次は一括承認とみなさず、それぞれ直前に対象と影響を示して明示承認を得る。

- Steam APIキー等の作成・登録
- Steamプロフィールやゲーム情報の公開範囲変更
- 実ライブラリ取得
- 実ウィッシュリスト取得
- 実Gemini調査
- 実Discord送信
- Obsidian専用選択ファイルの読み取り
- GitHub Actions scheduleの登録・有効化

接続テストは固定のテスト候補で1回から始め、秘密情報を表示しない。

### Step 5: 運用有効化

実データによる候補3本をユーザーが確認した後に限り、月曜6時5分のscheduleを有効化する。月曜24時の未選択時処理は、通知のみか第1候補の内部仮採用かを改めて確認してから有効化する。
