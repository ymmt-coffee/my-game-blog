## 1. 文書の位置づけ

本書は、ゲームブログの運営方針と自動化要件を定める詳細仕様である。

関連ファイルの役割は次のとおり。

| ファイル | 役割 |
|---|---|
| `docs/blog_automation_spec.md` | 人が読む詳細な運営・自動化仕様。本書 |
| `data/editorial/strategy.yaml` | AIと自動処理が参照する機械可読な設定 |
| `docs/roadmap.md` | 実装順、依存関係、完了条件 |

仕様が矛盾した場合は、本書で意図を確認し、確定値は `data/editorial/strategy.yaml` に合わせる。変更時は4ファイルを同時に更新する。

秘密情報、APIキー、Webhook URL、アクセストークンは、いずれのファイルにも保存しない。

### 1.1 現在の実装状況

2026-08-02時点で、Phase 0の監査と、Phase 1・2・3にまたがる安全な公開基盤の先行実装および実地確認が完了している。

## 2. プロジェクトの目的

### 2.1 出発点

やまもとが、趣味として文章を定期的に書き続けるための個人ブログを運営する。

趣味であっても結果を意識し、次を継続的に改善する。

1. 無理なく文章を書き続けられること
2. 再訪してくれる読者が増えること
3. 検索・SNSからのアクセスが増えること
4. 収益がブログ運営費とゲーム購入費へ近づくこと

1年後に月1万円の収益を得られれば成功と感じられる水準として、挑戦目標に置く。ただし、文章の趣味としての価値を損なってまで収益を優先しない。

### 2.2 想定読者

- 面白いPCゲームを探している日本語読者
- 攻略情報だけでなく、人が書いた文章を読むことを好む読者
- Steamのインディー作品、小規模開発作品、セール作品に関心がある読者

### 2.3 サイトの性格

- 攻略サイトではない
- 点数を付けて購入を断定するレビューサイトではない
- 一次体験と書き手の所感を中心にする
- 週次情報で新しい読者との接点を作り、月次エッセイで再訪理由を作る

## 3. 責任分界

### 3.1 やまもとが担当すること

- 候補3本からプレイするゲームを選ぶ
- ゲームを実際にプレイする
- プレイメモとスクリーンショットを残す
- 記事本文を書く
- AIの指摘を採用するか判断する
- ローカルプレビューを確認する
- 公開を最終承認する
- SNS上の返信や対話を手動で行う
- 新作・セール記事へ、可能な週は短い私感を加える

### 3.2 AIと自動処理が担当すること

- 毎週のゲーム候補3本と選定理由を作る
- 新作・セール記事の調査と下書きを作る
- 誤字、日本語、構成、SEO、事実確認について指摘する
- Hugoへの同期、Git記録、デプロイを行う
- 公開後のSNS投稿と再紹介を予約する
- Search Console、GA4、SNS、収益、ゲーム購入費を集計する
- 月次レポートと四半期編集会議の資料を作る
- 失敗や判断不能事項をDiscordへ通知する

### 3.3 AIに許可しないこと

- やまもとの記事本文を直接書き換えること
- AI自身がゲームを遊んだかのような一人称の感想を作ること
- 未確認情報、リーク、噂を事実として掲載すること
- SNSで自動返信、引用批評、議論への参加を行うこと
- 成人向け作品や強い残虐表現を中心とする作品を候補に含めること
- 公開承認前に記事を外部公開すること
- 秘密情報をObsidian、Git、ログ、Discord本文へ記録すること

## 4. コンテンツ設計

### 4.1 週次「プレイ途中記」

- 頻度: 原則週1本
- プレイ時間: 5時間を最低目標とし、その週に遊べるだけ遊ぶ
- 完走: 必須ではない
- 途中で継続が難しくなった場合: 実際のプレイ時間を明記して記事にする
- 星評価: 付けない
- 明確な購入判定: 載せない
- タイトル: 中立的にする
- ネタバレ: 原則扱わない。避けられない場合は冒頭へ警告する
- 公開が遅れた場合: 翌週へ持ち越し、新しいゲームを追加しない

冒頭には最低限、次を表示する。

```text
プレイ時間：約5時間
※本記事はゲーム全体を完走したレビューではなく、公開時点までのプレイに基づく所感です。
```

提供作品の場合のみ、提供の事実と編集上の独立性を表示する。

PCスペック、バージョン、使用言語、早期アクセス状態は常設項目にせず、本文の判断に関係するときだけ記載する。

### 4.2 週次「新作・セール5選」

- 公開: 月曜
- 対象期間: その月曜から日曜までに発売される作品
- 掲載数: 合計5本
- セール条件: 原則20%以上の割引
- 情報源: Steam、開発元、販売元の公式発表を一次情報とする
- SteamDB等: 発見と価格履歴の補助に限る
- AI: 公式情報を基に記事全体を下書きしてよい
- やまもと: 日曜24時までに短い私感を加える
- 私感がない場合: AI編集部の選定理由だけで予定どおり公開する

未プレイ作品の記事であり、レビューと誤認される表現を使わない。

### 4.3 月次レビューエッセイ

- 頻度: 余力がある月に1本
- 前提: フルプレイ、または十分に遊んだ作品
- 主目的: ゲーム体験を題材に好きな文章を書くこと
- 文体: 私小説的な要素を許容する
- SEO: 強く要求しない
- AI: 誤字や日本語上の違和感を指摘できるが、文体へ過度に介入しない
- SNS: 本文からやまもとの一節を引用して紹介する

### 4.4 記事を残す方針

- 販売終了、開発中止、大幅アップデート後も原則として記事を残す
- 軽微な誤字は履歴表示なしで修正できる
- 評価や事実関係に関わる変更は訂正履歴を残す
- 再紹介時は情報の鮮度を確認する

## 5. ゲーム選定

### 5.1 候補提示

AI編集長は毎週月曜6時5分にDiscordへ候補3本を提示する。

各候補には次を付ける。

- ゲーム名
- 選定理由
- 価格
- 日本語対応
- Steam評価
- 検索・話題性（5段階）
- やまもと適合度（5段階）

やまもとは月曜24時までにObsidianへ選択結果を書く。未選択の場合は第1候補を採用する。

候補が好みに合わなくても原則いずれかを選ぶ。ひどい選定が複数回続いた場合は、四半期を待たず選定基準を調整する。

### 5.2 選定優先順位

1. 発売直後などの話題性
2. 検索需要
3. やまもとの好みとの一致
4. 他ブログがまだ詳しく扱っていないこと
5. Steamでの評価
6. 価格の安さ
7. 日本語対応
8. 週次記事への適性
9. 月次エッセイへ発展できる可能性

### 5.3 嗜好

好みの参考ジャンル:

- MMO
- ストラテジー
- ビジュアルノベル
- シミュレーション
- ハクスラ
- ローグライク

好みの参考作品:

- Albion Online
- VA-11 Hall-A
- 世界樹の迷宮
- Tooth and Tail
- 不思議なダンジョンシリーズ

避ける傾向:

- システム上のテンポが悪い作品
- STG

ジャンルは固定条件にせず、新しいジャンルも候補にできる。

### 5.4 対象範囲と予算

- PC / Steam中心
- インディー・小規模開発を優先
- 特に関心が高い場合は大手作品も対象
- 早期アクセスを対象に含める
- AI生成素材を多く使う作品も通常どおり扱う
- 英語作品は、日本の一般読者が抵抗を感じにくい範囲で扱う
- 成人向け作品と強い残虐表現を中心とする作品は除外
- 一般的な戦闘、ホラー、軽度の流血表現は対象
- 候補は原則として未所有作品
- Steamライブラリとウィッシュリストを選定に利用する
- 通常の購入予算は月15,000円
- 特に注目すべき作品がある月のみ最大30,000円

## 6. Obsidianと記事構造

### 6.1 ディレクトリの役割

```text
Life_and_Div/
└─ 30_Projects/
   ├─ 01_blog/              # Obsidianで執筆する原稿
   └─ 10_Apps/
      └─ my-game-blog/      # Hugo、Git、公開処理
```

既存の同期スクリプトの監査は完了した。現在はこの構成を保ったまま、指定した1記事だけをHugoのPage Bundleへ同期する。

### 6.2 原稿フォルダ

```text
article-name/
├─ index.md
├─ review-report.md
└─ images/
   ├─ 01.png
   └─ 02.png
```

- やまもとが画像の選択、順序、キャプションを指定する
- 公開時に画像を必要に応じて圧縮・WebP化する
- `review-report.md` は証跡として残すが公開しない
- 校正レポートを記事本文へ追記しない

現在の同期処理は、原稿の `index.md` と `images/` を `content/posts/<slug>/` へ同期し、`review-report.md` を除外する。原稿の削除を公開記事の自動削除には連動させない。

## 7. 校正と公開

### 7.1 校正レポート

AIは次の分類で指摘する。

1. 誤字・脱字
2. 主語述語や日本語の違和感
3. 読者が理解しにくい箇所
4. 事実確認が必要な箇所
5. SEO上の提案
6. 構成上の提案

指摘はすべて提案であり、採用しなくても公開できる。

### 7.2 現在実装済みの公開フロー

1. Obsidianで `index.md` と記事ごとの `images/` を作成
2. `Alt+Shift+V` で一時領域へ同期し、ローカルプレビューを表示
3. やまもとが表示を確認し、公開する場合は `draft: false` にする
4. `Alt+Shift+P` を押し、確認画面で公開を明示承認
5. stage済み変更と対象記事の未コミット変更を検査
6. 指定した1記事だけをHugoの正式なPage Bundleへ同期
7. `draft: false`、必須ファイル、参照画像を検査
8. Hugoを出力なしでビルド検証
9. 対象記事だけを `publish: <slug>` でcommitし、GitHubへpush
10. GitHub Actionsの成功と公開URLのHTTP 200を確認

AI校正、Discord通知、SNS予約はこのフローへ後から追加する未実装工程である。校正を追加した後も、AIは本文を書き換えず `review-report.md` へ提案だけを記録する。

### 7.3 公開を停止する条件

- Hugoビルド失敗
- 必須記事ファイルの欠落
- 原稿が参照している画像の欠落
- GitHub Pagesへの公開失敗

文章、構成、SEO上の警告だけでは公開を止めない。

公開処理が失敗した場合はSNS投稿も停止し、Discordの `エラー通知` と `要確認` へ通知する。

## 10. SNS運用

### 10.1 アカウント

- 主軸: X
- 副配信先: Bluesky
- YouTube等: 後期拡張
- ブログ名決定後に、同一名・同一IDを優先して作成
- 公式アカウントは淡々とした編集部調で発信
- やまもとの個人アカウントを「中の人」として公開する
- 個人アカウントでも記事公開を毎回告知する

### 10.2 投稿方針

- AIは記事の要約、紹介、見どころ抽出を行う
- AIが体験者として感想を捏造しない
- 月次エッセイは、やまもとの本文から一節を引用する
- 自動返信を行わない
- 返信、引用、議論への参加はやまもとが行う
- ブログ公開成功を確認してから投稿する

### 10.3 再紹介

- 公開直後
- 翌日
- 1週間後
- 1か月後
- 関連セール開始時
- 大型アップデートまたは正式リリース時

定常的な自動再紹介は公開後1か月までとする。閲覧が伸びている記事は、鮮度を確認して臨時に再紹介できる。

記事が蓄積した段階で1日1投稿を上限とする定期運用を検討する。

## 11. 分析と編集判断

### 11.1 使用サービス

- Google Analytics 4
- Google Search Console
- X / Blueskyで取得可能な反応データ
- GitHub上の記事・公開履歴
- Obsidianに記録するゲーム購入費

GA4とSearch Consoleはブログ専用Googleアカウントで管理する。

### 11.2 月次レポート

詳細版をObsidianへ保存し、要約をDiscordの `アクセス月報` へ投稿する。

確認項目:

- 検索表示、クリック、CTR
- SNSからの記事流入
- 新規読者と再訪読者
- 記事公開後7日・30日の実績
- 週次記事と月次エッセイの差
- SNS投稿ごとの反応
- 収益とゲーム購入費
- 更新・再紹介する記事
- 翌月の企画方針

購入費の入力が間に合わない場合は未集計として公開し、後から更新できる。

### 11.3 四半期編集会議

3か月ごとに次を見直す。

- 扱うジャンル
- AI編集長の選定精度
- 更新頻度
- SNS投稿時刻と頻度
- 収益方法
- AI・自動化費用

AIは改善案を提示するが、運営方針はやまもとの承認後に変更する。

## 12. 収益化

### 12.1 初期方針

- 最初の20〜30記事は表示広告を置かない
- Steam等の公式販売ページへ、収益がなくてもリンクする
- アフィリエイトは正規販売元として確認できるサービスだけを使う
- 提供、広告、アフィリエイトの方針を固定ページで公開する

### 12.2 表示広告

アクセスと記事数が蓄積してからAdSense等を検討する。

- 記事末尾など、本文を分断しにくい場所へ少数配置
- 全画面広告を使わない
- 追従広告を使わない
- 大量の本文内広告を使わない
- 月次エッセイは広告を減らすか、広告なしにする

## 13. 提供作品

- 提供キーを受け付ける
- 記事掲載を保証しない
- 記事内容への指示を受けない
- ネガティブな内容も通常どおり掲載できる
- 提供の事実を記事に表示する
- 公開期限や禁則事項は事前合意がある場合のみ従う

## 14. 問い合わせ

ブログ専用Googleアカウントのメールを通知先とし、静的サイト向けフォームを設置する。

受け付ける内容:

- 記事の誤り
- 感想
- ゲームの推薦
- レビューキーの提供
- 広告、仕事の相談

フォーム項目:

- 名前
- メールアドレス
- 種別
- 本文

添付ファイルは受け付けない。スパム対策を導入し、Discordへは個人情報や本文を送らず「問い合わせあり」とだけ通知する。

## 15. 費用管理

AI API、X API、問い合わせフォーム等の自動化費用を合計月3,000円以内にする。

- 80%到達: Discordへ警告
- 100%到達: 次の順で機能を停止

停止順:

1. 過去記事の臨時SNS再投稿
2. 詳細なSNS分析
3. 臨時のAI調査
4. 通常のSNS再紹介

最後まで維持する機能:

- 記事公開
- 週次の候補選定
- 最低限の月次レポート
- エラー通知

ゲーム購入費は別枠とし、通常月15,000円、特別月最大30,000円とする。

## 16. バックアップ

### 16.1 対象

`Life_and_Div` 全体をGoogle Driveへ一方向バックアップする。ブログ専用Googleアカウントを使用する。

除外対象:

- `.git`
- Hugoの `public`
- キャッシュ
- 一時ファイル
- 仮想環境
- 再取得可能な依存ライブラリ

### 16.2 頻度

- 日次バックアップ: 毎日2時
- 月次スナップショット: 月初時点の状態を日付付きで固定保存
- 月次スナップショット保持数: 12
- 失敗時: Discordの `エラー通知` へ投稿

月次スナップショットは、破損や誤削除に気づく前の正常な状態へ戻るために保持する。

実装前に `Life_and_Div` の容量を測定し、Google Drive無料枠15GBへ収まるか確認する。

## 17. セキュリティと運用上の制約

- APIキーとWebhook URLはGitHub Secretsへ保存する
- 秘密情報をログへ出さない
- 外部投稿は公開成功後にだけ実行する
- 外部投稿の重複防止IDを保存する
- 同一処理を再実行しても二重公開しないよう冪等性を持たせる
- Git記録は記事単位で分かる名前を使う
- ユーザーの既存変更を自動的に巻き戻さない
- 自動処理の失敗は黙って無視しない
- AIが確認できない情報は記事へ入れず、校正レポートへ警告する
