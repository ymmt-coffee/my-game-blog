# ローカルブログ管理画面 基本仕様

## 1. 目的

ブラウザで開くローカル管理画面を、ブログ運営の唯一の中心にする。管理画面自体はWebへ公開せず、公開対象はHugoで生成したブログだけとする。

最初の完成条件は、管理画面だけで記事の新規作成、編集、画像管理、校正、プレビュー、公開ができることである。

## 2. 維持するもの

- Hugoと現在のブログコンテンツ
- Page Bundle形式の記事と画像
- 3種類の記事形式
- 公開前検査、ローカルプレビュー、記事単位の安全な公開
- AI校正の本文非自動変更方針
- レスポンシブ画像、SEO、固定ページ
- 毎日と月次の暗号化バックアップ

## 3. 管理画面

左メニューを固定し、次の画面を持つ。

1. 記事管理
2. スケジュール
3. AI編集部
4. 情報収集
5. リリース・セール情報
6. X投稿
7. アクセス解析
8. 設定・履歴

初期実装では記事管理だけを動作させ、後続画面は「準備中」と明示する。

Phase Bでlocalhost限定の画面土台を実装し、Phase C〜Lで記事管理、公開、予約、アクセス解析、X投稿案、情報収集、AI編集部、リリース・セール記事選定を追加済みである。通常起動は `admin/open-admin.ps1`、手動のサーバー起動は `admin/start-admin.ps1`、接続先は `127.0.0.1:8765` に固定する。デスクトップアイコンはPowerShell画面を表示せず、実行中の版が古い場合だけ、管理画面専用プロセスと確認して自動再起動する。

### 週次トップページ

管理画面のトップページは、月曜日から日曜日までを1週間として既存データを読み取り専用で集計する。月曜日に手動リセットは行わず、日付範囲を自動的に切り替える。記事、判断履歴、未完了作業は削除せず、未完了の記事は翌週の「次にやること」へ引き継ぐ。

トップには月曜日から日曜日までの作業目安を表示し、木曜日に「情報収集」ボタンを置く。このボタンは情報収集画面の週次更新と同じ処理を使い、処理済みの週は再実行しない。他の曜日は既存画面への作業目安とし、自動的な記事変更や公開は行わない。

週間ルーチンは、レビュー記事と新作・セール記事を並行して進める。レビューは日曜日までに次の対象ゲームを決め、翌週の日曜日までプレイと執筆を行い、その次の水曜日に予約公開する。新作・セールは木曜日に情報収集し、日曜日に公開する。2本目以降のレビューは余裕がある場合だけ追加し、必須の進捗判定には含めない。

- 今週の公開数、記事制作数、編集中、予約と、公開数・記事制作数の前週値
- エラー、今日の公開、公開準備完了、編集中、掲載候補選定、情報収集、X投稿案の順で最大3件の「次にやること」
- 今週作成・更新・公開・予約した記事、および前週から継続中の記事を最大5件
- 情報収集、候補選定、記事制作、公開、X投稿からなる新作・セール記事の進行
- プレイ候補、今週の購入、プレイ中、評価待ち

進捗は作業量の異なる項目を無理に割合へ変換せず、「未着手」「進行中」「要確認」「完了」と実数で表示する。問題がある場合だけ要確認欄を最上部へ表示する。アクセス数は週途中の進捗判定へ混ぜず、アクセス解析画面で確認する。集計のための新しい外部通信、AI実行、記事変更は行わない。

## 4. 記事管理

### 一覧

記事タイトル、種類、更新日、公開状態、予約日時、保存状態を表示する。タイトル・slugの画面内検索を備え、「下書き」「公開済」のタブで切り替える。slugは `YYYYMMDD-NNN` の日別連番で自動作成する。

### 編集

- タイトル、本文、概要、記事種類、公開日、画像を編集できる。
- 編集画面上部と記事一覧は、確定保存された最新タイトルへ連動する。
- 公開済み記事を保存した場合は「公開記事の更新下書き」として識別し、再投稿が完了するまで現在の公開版を維持する。
- 未確定の自動保存がある場合はプレビューと公開前チェックを停止し、履歴・復元から確認して手動保存させる。
- commit前の投稿失敗では公開準備完了を更新下書きへ戻す。旧公開版が存在する記事は更新作業中も公開済みタブへ表示する。
- 管理原稿と公開用コピーを本文・画像単位で照合し、一致、未公開の更新、公開コピー欠落を一覧で識別する。
- Markdownを保存形式とする。
- 見出し、リンク、画像を挿入する補助操作を用意する。
- 自動保存と手動保存を区別して状態表示する。
- 画像は記事ごとの `images/` に保存し、元画像を勝手に上書きしない。
- 画像欄にサムネイルと `![代替文](images/ファイル名)` 形式を表示し、本文へコピーしてそのまま画像表示に使えるようにする。
- アップロード済み画像は明示操作で記事のヘッダー画像に設定・解除できる。本文中の画像をヘッダー画像や一覧サムネイルへ自動転用しない。
- 本文の手動保存と履歴・復元は本文欄の右上に置き、新規作成・下書きでは編集画面下部のアーカイブ欄を表示しない。
- プレイログは新規作成・編集時に「未クリア」「クリア」を選択できる。未クリアの場合だけプレイ時間と未完走である旨を公開記事へ表示し、クリアの場合はこの注意書きを表示しない。項目のない既存記事は未クリアとして扱う。

### 記事状態

`draft`、`review_pending`、`ready`、`scheduled`、`published`、`archived` を基本状態とする。ファイルのfront matterと補助データが矛盾する場合は公開を止める。

### 操作

- 保存
- プレビュー
- 公開前チェック
- 投稿
- 予約
- 削除（復元可能な論理削除）

投稿と予約は確認画面を必須とし、対象記事、公開先、検査結果、警告を表示する。

### Phase C実装状況

`content/articles/<slug>/index.md` と `images/` を正本とする記事管理を実装済みである。新規作成、一覧、編集、自動保存、手動保存、履歴からの復元候補、画像追加、競合停止、外部変更の明示取り込み、論理アーカイブを管理画面から利用できる。

個人利用向けの調整として、自動slug、記事検索、一覧からの復元可能な削除を追加した。削除した記事は正本ファイルを保持し、「設定・履歴」の復元欄から戻せる。移行前原稿の確認入口は記事一覧へ表示しない。

公開用コピーは正本にせず、管理原稿から生成する配置を維持する。公開側だけに存在する記事は「設定・履歴」に表示し、ユーザー操作で管理原稿へ非破壊コピーできる。同名の管理原稿がある場合は停止し、公開記事や既存原稿を自動削除・上書きしない。

公開中の記事を一覧から除く場合は、通常の論理削除と区別した「公開停止」を使う。slug確認後、対象の公開用コピーだけを記事限定commit・pushで削除し、管理原稿は復元可能な状態で保持する。公開コピーと同一の記事を復元した場合は、変更なしの再投稿を求めず公開済みへ再照合する。

移行前の外部テスト原稿3件は2026-08-09のユーザー承認によりWindowsのごみ箱へ移動し、外部原稿フォルダは空になった。記事一覧には移行前原稿の確認入口を表示しない。

## 5. 記事テンプレート

初期版は次の3種類を扱う。

- プレイログ `play_note`
- 新作・セール `weekly_picks`
- 月刊コラム `monthly_essay`

テンプレートは本文の雛形だけでなく、記事種類ごとの必須入力、注意表示、検査条件をまとめる。後からテンプレートを追加できる構造にする。

### Phase D実装状況

3カテゴリーを独立した定義として実装する。プレイログと月刊コラムは空の本文から作成し、新作・セールだけ本文雛形を生成する。共通必須項目に加え、`play_note` は `play_time` を必須とする。カテゴリーごとの注意事項と必須項目検査を編集画面へ表示する。

執筆途中の内容を失わないため、検査エラーがあっても下書き保存は可能とする。公開可否の停止判定はPhase Eで同じ検査を再利用する。カテゴリー変更時は既存本文を勝手に雛形で上書きせず、未知のfront matterキーも保持する。

## 6. データ

- 記事本文: Markdown
- 記事画像: 通常の画像ファイル
- 公開ブログ: Hugo
- 状態、予定、処理履歴: ローカルSQLite
- 秘密情報: 環境変数または現在の保護済み外部設定

SQLiteが壊れても記事本文と画像を読み出せることを必須とする。本文保存と状態保存の不整合を検出し、黙って公開しない。

## 7. 公開

管理画面は既存の安全な公開処理を機能単位で再利用する。公開前に校正状態、必須項目、画像、内部リンク、Hugoビルド、生成サイトを確認する。公開処理は対象記事だけをcommitし、承認後だけpushする。

GitHub Pagesのビルドと公開は維持し、公開サイトの正規URLは `https://framing-games.com/` とする。従来の `https://ymmt-coffee.github.io/my-game-blog/` はGitHub Pagesの転送元として残す。Discord通知は使用しない。

Hugoの時刻基準は `Asia/Tokyo` とし、記事日付、プレビュー、予約、公開判定を日本時間へ統一する。日本時間では当日でもUTCでは翌日となる時間帯に、当日記事を未来記事として除外しない。

### Phase E実装状況

管理画面からAI校正、指摘ごとの採用・見送り、Hugoプレビュー、公開前チェック、最終確認、記事単位のcommit・push、Pagesと公開URL確認を実行できる。AI校正は本文を自動変更せず、校正結果は `var/admin/reviews/` に置いて公開対象から分離する。

AI校正は操作のテンポを優先して現在停止・非表示としている。過去の校正記録と実装は保持するが、現在の公開前チェックでは校正を必須条件にしない。

公開前チェックは必須項目、秘密情報、画像、内部リンク、Hugo本番ビルド、生成HTMLを確認する。合格時に記事ハッシュと15分間有効な一回限りの承認を固定し、最終画面で対象slugが一致した場合だけ投稿する。検査後に原稿や状態が変われば承認を無効にする。

投稿時は既存stage、公開コピーの未コミット変更、対象外stageを停止条件とし、`content/articles/<slug>/` と `blog/content/posts/<slug>/` だけをcommitする。push後は対応するGitHub Actionsと公開URLのHTTP 200を確認してから公開済みと記録する。

公開リポジトリの誤commit防止として、Gitへ登録済みの内容だけを読む共通検査を設ける。秘密鍵、既知形式のAPI token、Steam Web API key、個人ホームの絶対パス、`review-report.md`、`.env`、`var/`、`backup-source/` を検出した場合はcommit前に停止する。管理画面の記事公開と公開停止、ローカルGit hook、GitHub Actionsは同じ検査を使用し、検査自体を通過できない場合も安全側で停止する。

### Phase F実装状況

公開ブログを明るいグレー、黒、濃淡グレーで構成する直線的なゲームメディア風デザインへ更新した。ブログ名は `FRAMING` とし、最新記事1件を大きく表示した後に記事一覧を配置する。メニューはプレイログ、新作・セール、月刊コラム、About、検索で構成する。

記事のヘッダー画像にはfront matterの `cover.image` で明示された画像だけを使用する。設定されていない記事はカテゴリー別の共通表示を使い、本文中の画像を自動抽出しない。管理画面ではアップロード済み画像ごとに設定・解除でき、公開済み記事で変更した場合も通常の更新下書きと同じ安全な再投稿手順を使う。

PCとモバイルの一覧・記事ページを確認し、広告を置かない状態でも専用の空白を作らない構成とした。トップページのLATESTは画像と記事情報を横並びにした縦型リストとし、将来はリスト右側へ広告列を追加できる構造にするが、現在は広告枠や空白を表示しない。

Phase A〜F完成後のリファクタリングでは、管理画面の記事入力解釈、公開ブログの記事種別名、トップ記事順、LATEST、日付表示をそれぞれ共通部品へ整理した。記事データ、URL、保存・公開の安全処理と画面上の挙動は変更しない。

## 8. 予約とカレンダー

まず記事編集画面に予約日時と予約解除を実装し、その後に月・週カレンダーを作る。カレンダーは記事公開、SNS投稿、発売日、セール終了日など、各機能が持つ予定の統合表示とする。

Phase Gでは記事の予約前チェック、確認画面、予約確定、解除、期限到来時の公開処理を実装した。確認時の原稿ハッシュと検査済みコピーが一致する場合だけ、指定時刻以降に対象記事をcommit・pushする。管理画面が停止していた場合は、次回起動時に期限を過ぎた予約を処理する。予約後の原稿変更、準備済みコピー欠落、Git・Pages異常では公開せず、記事を公開準備完了へ戻して安全な理由を残す。

カレンダーは月表示と週表示を持ち、現在は記事の予約日時、公開日時、毎月1日20:00の前月アクセス解析レビューを表示する。将来のSNS投稿、発売日、セール終了日は、各Phaseでデータが確定した後に同じ画面へ追加する。

## 9. 後続機能

### アクセス解析

取得、数値表示、比較、改善提案の順で段階導入する。外部解析サービスはUmami Cloudを採用し、公開サイトへの接続と実地計測を確認済みである。

Phase Hのローカル範囲では、UTF-8の集計済みCSVまたはUmamiの `website_event.csv` を読み込み、SQLiteには `date`、`path`、`views`、`visitors` に相当する日別・ページ別の集計値だけを保存する。7・30・90日の集計、直前期間比較、日別閲覧数、上位ページ、ルールベースの確認候補を表示する。同一データ元・日付・ページは再取込で置き換え、二重加算しない。セッションID、IPアドレス、Cookie、ユーザーエージェント、端末、地域、参照元の生データは保存しない。

公開サイトではUmami CloudのHobbyプランを利用する。独自ドメイン移行後は `framing-games.com` だけを計測し、検索パラメーターとハッシュを除外し、Do Not Trackを尊重する。自己アクセスはブラウザのlocalStorage設定で除外する。旧 `ymmt-coffee.github.io/my-game-blog/` のエクスポートは履歴として引き続き取り込める。当面はUmami画面で確認し、手動エクスポートの `website_event.csv` を管理画面へ取り込む。API自動取得のためだけには有料化しない。

月次レビューではUmamiから前月分を手動でエクスポートし、`website_event.csv` を日別・ページ別の匿名集計値へ変換して取り込む。個別のセッションID、端末、地域、参照元等は保存しない。よく読まれた記事、伸びたカテゴリー、次に書く候補の方向性を確認する。解析結果は判断材料に限定し、記事の自動選定・自動生成・自動公開には使わない。

### SNS

投稿案作成、人による確認、手動投稿、予約投稿、結果取得、自動化の順に進める。初期状態では外部投稿を行わない。

Phase Iの初期範囲では投稿先をXに固定する。公開中の内容と一致する記事を選び、タイトル、概要、公開記事URLから280文字以内の投稿案を作る。投稿文は管理画面内で編集・コピーでき、「確認済み」とした後に、Xへ手動投稿したことと任意の投稿URLを記録する。投稿案作成時から記事が変更された場合は、古い案の確認と手動投稿済み記録を停止する。

投稿案と状態はローカルSQLiteだけに保存し、Xへ通信しない。X APIの導入、投稿予約、結果取得、自動投稿、カレンダー統合は保留する。Blueskyは当面利用せず、将来必要性が生じた場合だけ再検討する。

### 情報収集

ゲーム名、App ID、発売日、価格、割引、日本語対応、評価、公式URL、確認日時、情報源などを共通データとして扱う。AIは候補発見と文章案に限定し、価格等の確定をAIの自己申告だけに依存しない。

Phase JではSteamで日本から購入でき、日本語のインターフェースまたは字幕に対応するシングルプレイ可能なPCゲームを対象とする。ホラー、オンライン専用、DLC、サウンドトラック、ゲーム内商品、体験版、成人向け専用作品、非ゲーム商品、日本から購入できない作品は除外する。早期アクセスと条件を満たす基本無料ゲームは対象に残す。

毎週木曜日8:00 JSTに、AUTOMATON、4Gamer.net、Game*Sparkの登録済み取得元とSteamから候補を収集する。RSS由来を最大30本、Steam直接発見を新作10本・セール10本の最大20本とし、Apify照会は合計50本を上限にする。PCまたは管理画面が停止していた場合は、次回起動時に未実行分を補う。初回はApify最大10本の手動試運転を行い、日本円、日本語対応、費用、候補品質を確認してから定期実行を有効にする。

Apifyは無料プランを前提に月4米ドル相当で停止し、Geminiは無料枠内で固定採点後の上位13本の説明だけを週1回生成する。取得やAI説明に失敗した場合は前回情報または固定採点を表示し、処理全体を不必要に停止しない。外部接続の範囲、保存項目、採点条件、履歴期間は `phase-j-shared-game-information-design.md` を正本とする。

Phase Jでは、ゲーム、最小限のSteam同期状態、出典、価格履歴、候補と点数内訳、ユーザー判断、収集実行履歴、候補説明をSQLite schema version 9として実装した。外部入力は保存前にApp ID、URL、日付、価格、列挙値、文字数を検査し、ゲーム本体・出典・価格は一つのトランザクションで保存する。リリース・セール画面では保存件数、最終収集、候補、固定採点を補足するAI説明を確認できる。使用中DBは日次・月次バックアップ直前に整合性を検査した複製へ置き換え、`var/` を直接コピーせず暗号化バックアップへ含める。

RSS 2.0・Atomの件数と容量を制限した読取、Steam App ID抽出、Steam日本向け公開応答の検査・共通形式化を実装した。4Gamerは公式RSSの見出しと短い要約だけを候補名へ照合し、掲載媒体数を話題性へ加点する。残る2媒体は正式な取得方法を確認するまで接続しない。Apify、Steam、Geminiの秘密情報は環境変数の設定有無だけを確認し、値を画面、DB、ログへ出さない。

試運転合格後の週次収集は木曜8:00 JSTにSteam新作10件・セール10件を処理し、停止中に期限を過ぎた場合は次回管理画面起動時に同じ週を一度だけ補完する。管理画面の「今週の情報をまとめて更新」でも同じ週次処理を明示実行でき、Steam所有ゲーム同期、候補収集、媒体確認、固定採点、候補説明を1操作で行う。自動または手動のどちらかが完了した週は実行IDを共有して重複実行しない。Steam認証情報がある場合は公式 `GetOwnedGames` を先に同期し、App IDと所有状態だけを反映する。ウィッシュリストは正式な取得方法を確認できるまで接続しない。実行前にApify公式の月間利用額を確認し、4米ドル以上では停止する。Geminiへ送るのは上位13件のタイトル、固定採点、公開価格・発売日・レビュー、媒体名だけで、Steam App IDや原稿本文は送らない。固定3件の接続確認、最大10件の試運転、所有ゲーム単独同期は診断用として折り畳み表示する。

現行のSteam候補発見は、実行時点の公開一覧スナップショットを使う。設計値として初回7日・補完最大14日を保持しているが、過去日の一覧を遡る処理は未実装である。週の途中で初回収集した場合、その時点の最新リリースへ候補が偏る可能性があるため、直近期間の遡及収集は本番運用調整として別途判断する。

Apifyは `fetch_cat/steam-store-games-scraper` を候補発見と基本情報取得用に固定した。手動3件試験では3件成功、日本円価格取得、費用0.005米ドルを確認した。日本語対応、レビュー、セール終了日時はSteam日本向け公開情報で補完する。管理画面のAPI接続確認は固定3件、Bearer認証、5MB応答上限、24時間再実行停止を適用し、正式試運転は最大10件のままとする。

最大10件の正式試運転は、Steam日本向け公開一覧から新作5件とセール5件を重複排除して発見し、ApifyとSteam日本向け詳細で補足する。日本語、シングルプレイ、ホラー、評価、価格、新作期間、割引率を固定条件で候補・要確認・除外へ分類し、点数と除外理由を管理画面へ保存する。外部接続は「最大10件で候補試運転」を押した場合だけ行い、記事作成、購入、公開、SNS投稿には進まない。

### AI編集部、情報収集、リリース・セール情報

共通情報収集基盤の後に実装する。採用操作から記事下書きを作れるようにするが、購入、公開、SNS投稿を自動承認しない。

AI編集部は「次に購入・プレイするゲーム」と「次に書く記事」の両方を扱う。上位3本は原則として新作・近日発売を1本、セール・無料配布を1本、残りを総合点最上位とする。自分の興味35%、話題性25%、Steam評価15%、価格・割引15%、記事の多様性10%を初期配分とし、十分なアクセス実績ができるまでは閲覧数を参考表示だけにする。

候補は「プレイ候補」「記事候補」「保留」「興味なし」で管理する。記事下書き、購入記録、プレイ開始、公開、SNS投稿はいずれも人の操作を起点とする。AIは推薦理由と記事形式を提案できるが、価格等の事実確定、購入、本文変更、公開を行わない。

Phase Kでは、最新周期の有効候補から、新作・近日発売とセール・無料配布を存在する範囲で1本ずつ含め、残りを総合点順にした最大3本をAI編集部へ表示する。説明はPhase Jで保存済みのGemini説明を使い、説明がない場合は固定採点の候補をそのまま表示する。画面表示だけでAIを再実行しない。プレイ候補・記事候補は判断から4週間、保留は2週間、興味なしは通常の再提案から除外する。判断・購入・プレイ記録は管理画面から個別に削除できる。記事企画の関連解除では記事本体を削除せず、記事の削除は記事管理画面の既存手順に分離する。

AI編集部では、候補判断、購入日・価格、プレイ状況、簡単な評価、記事形式を記録できる。月間購入合計は通常10,000円、明示確認した例外を含め20,000円で停止し、決済情報は保存しない。記事形式はプレイログ、新作・セール、月刊コラム、記事化せずプレイのみから提案する。

記事下書きは「下書きを作成」を押した場合だけ、既存の記事管理へ通常のMarkdownとして作る。概要と、プレイログの場合はプレイ時間を意図的に未入力とし、記事管理で完成させるまで公開前検査を通さない。AI編集部は記事本文を作成・変更せず、commit、push、公開、SNS投稿も行わない。状態、購入、評価、下書きとの対応はSQLite schema version 10へ保存する。

Phase Lでは収集結果の確認と、週刊記事の掲載候補選定を別画面へ分ける。「情報収集」は収集準備、外部接続の明示実行、最新周期の新作、セール・無料、その他、除外理由、公式情報再確認、発売日・セール終了日のカレンダー選択を扱う。候補の公式情報再確認は人がボタンを押した場合だけSteam日本向け公開情報へ接続し、画面を開くだけでは外部通信しない。

「リリース・セール情報」は最新周期の有効候補から、週刊記事へ載せる新作を最大5本、セール・無料を最大5本選ぶ。選択状態はSQLite schema version 12へ保存し、選択した内容から週刊記事1本の下書きを作る。下書き作成時は選択した全候補を同じ操作内でSteam公式情報に再確認し、1件でも失敗した場合は記事を作成しない。作成物は `weekly_picks` の未完成・未公開Markdownであり、事実欄と選定理由は人が記事管理で完成させる。公開、SNS投稿へ自動的に進めない。

候補の発売日とセール終了日は、日付が確認できる場合だけ個別の明示操作でカレンダーへ追加・解除できる。選択状態はSQLite schema version 11へ保存する。日付が失われた場合は誤った予定を推測せず表示しない。

## 10. 保留済み機能
