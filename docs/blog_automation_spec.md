# ローカルブログ管理画面 基本仕様

## 1. 目的

ブラウザで開くローカル管理画面を、ブログ運営の唯一の中心にする。管理画面自体はWebへ公開せず、公開対象はHugoで生成したブログだけとする。

最初の完成条件は、管理画面だけで記事の新規作成、編集、画像管理、校正、プレビュー、公開ができることである。

## 2. 維持するもの

- Hugoと現在のブログコンテンツ
- Page Bundle形式の記事と画像
- 3種類の記事形式
- 公開前検査、ローカルプレビュー、記事単位の安全な公開
- AI校正の本文非自動変更方針
- レスポンシブ画像、SEO、固定ページ
- 毎日と月次の暗号化バックアップ

## 3. 管理画面

左メニューを固定し、次の画面を持つ。

1. 記事管理
2. スケジュール
3. AI編集部
4. リリース・セール情報
5. SNS分析
6. アクセス解析
7. 設定・履歴

初期実装では記事管理だけを動作させ、後続画面は「準備中」と明示する。

Phase Bでlocalhost限定の画面土台を実装済みである。通常起動は `admin/open-admin.ps1`、手動のサーバー起動は `admin/start-admin.ps1`、接続先は `127.0.0.1:8765` に固定する。現時点では記事操作も含めて各業務機能は準備中であり、Phase Cから記事管理を有効にする。

## 4. 記事管理

### 一覧

記事タイトル、種類、更新日、公開状態、予約日時、保存状態を表示する。絞り込みは下書き、校正待ち、公開準備完了、予約済み、公開済み、アーカイブを対象とする。

### 編集

- タイトル、本文、概要、記事種類、公開日、画像を編集できる。
- Markdownを保存形式とする。
- 見出し、リンク、画像を挿入する補助操作を用意する。
- 自動保存と手動保存を区別して状態表示する。
- 画像は記事ごとの `images/` に保存し、元画像を勝手に上書きしない。

### 記事状態

`draft`、`review_pending`、`ready`、`scheduled`、`published`、`archived` を基本状態とする。ファイルのfront matterと補助データが矛盾する場合は公開を止める。

### 操作

- 保存
- 校正
- プレビュー
- 公開前チェック
- 投稿
- 予約
- アーカイブ

投稿と予約は確認画面を必須とし、対象記事、公開先、検査結果、警告を表示する。

## 5. 記事テンプレート

初期版は次の3種類を扱う。

- プレイ途中記 `play_note`
- 新作・セール5選 `weekly_picks`
- 月次レビューエッセイ `monthly_essay`

テンプレートは本文の雛形だけでなく、記事種類ごとの必須入力、注意表示、検査条件をまとめる。後からテンプレートを追加できる構造にする。

## 6. データ

- 記事本文: Markdown
- 記事画像: 通常の画像ファイル
- 公開ブログ: Hugo
- 状態、予定、処理履歴: ローカルSQLite
- 秘密情報: 環境変数または現在の保護済み外部設定

SQLiteが壊れても記事本文と画像を読み出せることを必須とする。本文保存と状態保存の不整合を検出し、黙って公開しない。

## 7. 公開

管理画面は既存の安全な公開処理を機能単位で再利用する。公開前に校正状態、必須項目、画像、内部リンク、Hugoビルド、生成サイトを確認する。公開処理は対象記事だけをcommitし、承認後だけpushする。

GitHub Pagesのビルドと公開は維持する。Discord通知は使用しない。

## 8. 予約とカレンダー

まず記事編集画面に予約日時と予約解除を実装し、その後に月・週カレンダーを作る。カレンダーは記事公開、SNS投稿、発売日、セール終了日など、各機能が持つ予定の統合表示とする。

## 9. 後続機能

### アクセス解析

取得、数値表示、比較、改善提案の順で段階導入する。外部解析サービスはユーザー承認後に接続する。

### SNS

投稿案作成、人による確認、手動投稿、予約投稿、結果取得、自動化の順に進める。初期状態では外部投稿を行わない。

### 情報収集

ゲーム名、App ID、発売日、価格、割引、日本語対応、評価、公式URL、確認日時、情報源などを共通データとして扱う。AIは候補発見と文章案に限定し、価格等の確定をAIの自己申告だけに依存しない。

### AI編集部とリリース・セール情報

共通情報収集基盤の後に実装する。採用操作から記事下書きを作れるようにするが、購入、公開、SNS投稿を自動承認しない。

## 10. 保留済み機能

Discord通知、週次AI調査、旧週次5選生成、旧Phase 6案は `archive/` へ退避した。現在の管理画面仕様へ再設計するまで実行しない。

## 11. Phase A設計状況

データ構造と移行の確定設計は `phase-a-data-migration-design.md` にまとめた。正本はリポジトリ内の `content/articles/`、管理台帳は `var/admin/admin.sqlite3`、技術構成はFastAPIと通常のHTML・CSS・JavaScriptとする。

これらは2026-08-09にユーザー承認済みであり、Phase Aは完了した。ただしPhase Cで記事ごとの安全な移行を承認・実行するまでは、外部原稿を正本とする現在のObsidian暫定運用を維持する。Phase Bの実装、依存追加、原稿移行は各Phaseの承認範囲で行う。
