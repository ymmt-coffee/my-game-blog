# 記事の校正・プレビュー・公開手順

## 現在の位置づけ

Phase Gの完成後は、通常の記事操作と予約公開をローカル管理画面で行う。この文書は管理画面の操作手順と、移行前原稿に限る従来経路を示す。

Discord通知は使用しない。

公開ブログの正規URLは `https://framing-games.com/` である。従来のGitHub Pages URLは移行用の転送元として扱い、新しい記事URLやX投稿案には使用しない。

## 管理画面での通常手順

1. デスクトップの「ゲームブログ管理」を開き、記事を選ぶ。
2. 記事を確定保存する。
3. 「プレビュー」で表示を確認する。
4. 「公開前チェック」を押す。
5. 合格画面で対象、公開先、警告、原稿ハッシュを確認し、「投稿を実行」を押す。
6. Pages完了画面を確認する。

公開前チェックの承認は15分間、一回だけ有効である。検査後に原稿が変わった場合は再検査する。

## 予約公開

1. 記事を入力し、必要ならプレビューする。
2. 編集画面の「予約公開」で未来の日時を入力し、「予約前チェック」を押す。この時点の画面内容は、手動保存と同じ履歴・競合検査を通して自動的に確定保存される。
3. 確認画面で対象記事、公開日時、公開先、警告を確認する。
4. 「この日時で予約する」を押す。この操作を、指定時刻以降に対象記事だけをcommit・pushする明示承認として扱う。
5. 変更する場合は編集画面から「予約を解除」し、修正・確定保存後に予約をやり直す。

予約後は確認時の原稿ハッシュを固定する。原稿が変わった場合、検査済みコピーがない場合、GitやPagesで異常が起きた場合は自動公開せず「公開準備完了」へ戻し、編集画面へ理由を表示する。

管理画面が起動中なら指定時刻を定期確認する。PC停止中や管理画面停止中に時刻を過ぎた予約は、次回起動時に処理する。そのため、指定時刻ぴったりの公開が必要な場合は、PCと管理画面を起動しておく。

左メニューの「スケジュール」では月・週を切り替え、記事の予約日時、公開日時、毎月1日20:00の「前月アクセス解析レビュー」を確認できる。月次レビューではUmami Cloudから前月分を手動でエクスポートし、`website_event.csv` をアクセス解析画面へ取り込む。よく読まれた記事と次に書く方向性を確認するが、記事の選定や公開は自動実行しない。

## 公開済み記事の更新

公開済み記事を編集している間、自動保存は復元用領域にだけ保存され、公開ページは変わらない。手動保存すると管理用原稿を「公開記事の更新下書き」として保存し、公開中の旧版は維持する。更新下書きが途中のまま残ってもWebへ公開されない。

手動保存されていない自動保存がある場合、プレビューと公開前チェックは停止する。編集画面の案内から「履歴・復元」を開き、自動保存内容を確認して手動保存してから再実行する。commit前に投稿が失敗した場合は、公開準備完了のまま残さず「公開記事の更新下書き」へ戻す。旧公開版がある記事は更新作業中も公開済みタブから確認できる。

修正完了後にプレビュー、公開前チェック、最終確認、投稿を行うと更新版が公開される。手動保存前の内容は履歴へ退避されるため、必要に応じて「履歴・復元」から確認できる。

## 原稿

管理画面の記事は `content/articles/<記事slug>/` のPage Bundleを正本として扱う。移行前の外部テスト原稿は2026-08-09にユーザー承認を得てWindowsのごみ箱へ移動済みで、現在の外部原稿フォルダは空である。

公開用コピーは `blog/content/posts/<記事slug>/` に置く。管理画面は正本と公開用コピーの本文・画像を照合し、一覧へ次の状態を表示する。

- `公開済み`: 正本と公開用コピーが一致している。
- `更新あり`: 公開中の旧版を維持したまま、正本に未公開の修正がある。
- `公開差異・要確認`: 公開済みの記録があるが公開用コピーを確認できない。

公開側だけにある記事は「設定・履歴」の「公開側だけの記事」から管理画面へ取り込む。取り込みは公開記事を変更せず、正本へコピーして `draft: true` にする。同じslugの正本がある場合は停止する。

下書きの「削除」はローカルの論理削除だけを行う。公開中の記事は「公開停止」を選び、確認画面でslugを入力した後、対象の公開用コピーだけをcommit・pushしてサイトから取り下げる。管理原稿は削除せず「設定・履歴」に保持する。公開中の内容と同一の記事を復元した場合は公開済みへ戻るため、変更のない再投稿は不要である。

```text
<記事slug>/
├─ index.md
├─ review-report.md
└─ images/
```

- 公開本文は `index.md`。
- 校正記録は `review-report.md`。公開対象へ含めない。
- 画像は記事ごとの `images/` に置く。
- 画像を使わない記事では `images/` フォルダは空でも構わず、公開処理は実画像または追跡済み画像の変更がある場合だけ画像パスをcommit対象にする。
- 一覧と記事上部へ表示する画像は、管理画面の画像欄で「ヘッダー画像に設定」したものだけを使う。設定しない場合はカテゴリー別の共通表示になり、本文画像は自動転用されない。
- ヘッダー画像の設定・解除も記事本文の変更として扱う。公開済み記事では更新下書きになり、手動保存、プレビュー、公開前チェック、最終確認、投稿の順で公開版へ反映する。
- 執筆中は `draft: true`、公開時だけ明示的に `draft: false` とする。

## 記事種類

- `play_note`: プレイログ。`play_time` が必須。
- プレイログの `game_completed` は管理画面の「未クリア」「クリア」に対応する。未設定の既存記事は未クリア扱いとなり、クリア済みでは未完走の注意書きを表示しない。
- `weekly_picks`: 新作・セール。未プレイ情報記事として表示する。
- `monthly_essay`: 月刊コラム。

## 情報収集とリリース・セール記事の作成

### 週間更新ルーチン

- 日曜日までに、次のレビュー対象ゲームを決める。
- 翌週の日曜日まで、レビュー対象ゲームをプレイしながら原稿を仕上げる。
- 完成したレビュー記事は、その次の水曜日に予約公開する。
- 新作・セール記事は木曜日に情報収集し、候補選定と執筆を進めて日曜日に公開する。
- 2本目以降のレビューは、余裕がある週だけ追加する。

- 通常の週次作業は、木曜日8:00以降に「情報収集」の「今週の情報をまとめて更新」を1回押す。Steam所有ゲーム同期、新作・セール候補収集、媒体情報の確認、固定採点、候補説明までを同じ処理で行う。
- 同じ週の更新済みデータがある場合は再実行せず「今週分は更新済み」と表示する。木曜日8:00以降に管理画面が先に自動更新した場合も、追加操作は不要である。
- Steam候補は収集時点の新作・セール公開一覧から取得する。現在は過去日の一覧を遡らないため、週の途中で初回実行した場合はその時点の最新候補へ偏ることがある。処理済み記録だけを消して再実行しても過去日分は補えない。
- 「3件でAPI接続を確認」「最大10件で候補試運転」「所有ゲームを今すぐ同期」は「接続テスト・個別操作」内の診断用とし、通常の週次作業では使わない。
- 「情報収集」は最新の収集周期を新作、セール・無料、その他、除外へ分け、除外理由と収集状態を表示する。
- 「情報収集」の「公式情報を再確認」はSteam日本向け公開情報をその場で再取得する。画面を開くだけでは外部接続しない。
- 発売日・セール終了日は「情報収集」で、日付が確認できる候補だけを個別にカレンダーへ追加・解除する。
- 「リリース・セール情報」で、週刊記事に載せる新作を最大5本、セール・無料を最大5本選択する。
- 「選択した内容から記事下書きを作成」は選択全件の公式再確認に成功した場合だけ、1本の未完成・未公開 `weekly_picks` を作る。1件でも失敗した場合は作らない。
- 作成後は記事管理で、選定理由、注目ポイント、価格・期間、日本語対応などを確認して完成させる。
- これらの操作は記事本文の生成、購入、公開、X投稿を自動実行しない。

記事日付、プレビュー、公開判定はHugoの `Asia/Tokyo` 設定により日本時間へ統一する。日本時間の日付がUTCでは翌日になる時間帯でも、当日記事を未来記事として除外しない。

## 校正

管理画面のAI校正は、操作のテンポを優先して現在停止・非表示としている。公開前チェックでも校正結果を必須にしない。過去の校正記録は削除しない。

```powershell
.\tools\publishing\review.ps1 -Article <記事slug> -Gemini
```

校正は本文を自動修正しない。指摘を確認し、採用する内容だけ人が本文へ反映する。APIキーは環境変数からだけ読み、値を表示しない。

## プレビュー

```powershell
.\tools\publishing\preview.ps1 -Article <記事slug>
```

必須項目、画像、内部リンク、秘密情報を検査してからローカルHugoサーバーを起動する。

## 公開

```powershell
.\tools\publishing\publish.ps1 -Article <記事slug> -Approve
```

公開処理はfront matter、画像、リンク、Hugo本番ビルドを検査し、対象記事だけをcommit・pushする。GitHub Pagesの成功と公開URLのHTTP 200を確認する。commitとpushを伴うため、公開前チェックとは別の最終確認ページで「投稿を実行」を押す。slugの再入力は求めない。

## 移行前原稿の暫定経路

現在、移行前原稿は存在しない。従来の外部Obsidian経路は使用せず、通常操作は管理画面で行う。
