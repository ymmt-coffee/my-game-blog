# 運営自動化の共通実装ルール

## 1. 目的

この文書は、`my-game-blog` の各Phaseで繰り返し適用する調査、実装、安全、テスト、Git、資料更新、報告の共通ルールを定める。

Phase固有の目的、外部サービス、通知先、テストケース、完了条件は、各Phaseのプロンプトと実装報告で追加する。この文書へ、モデル名、ショートカット、Secret名、バージョンなど変更され得る現在値を重複記載しない。

## 2. 資料の役割と優先順位

作業開始時は次を確認する。

1. リポジトリ直下の `AGENTS.md`
2. 本書 `docs/automation-common-rules.md`
3. `docs/README.md`
4. `docs/blog_automation_spec.md`
5. `docs/roadmap.md`
6. `data/editorial/strategy.yaml`
7. `docs/publishing-workflow.md`
8. 対象Phaseの直前までの実装報告
9. Phase固有プロンプトで指定された資料

判断時は次を優先する。

- 現在のコードと自動テスト
- 現在の操作手順である `docs/publishing-workflow.md`
- 最新の実装報告
- 詳細方針である `docs/blog_automation_spec.md`
- 機械可読な確定値である `data/editorial/strategy.yaml`
- 過去の監査・実装報告

コードと資料の不一致を見つけた場合は、どちらかを無条件に正しいとみなさず、現在動作、履歴、影響範囲を確認する。サービス、モデル、実行方法、Secret名、ショートカット、公開条件などユーザー判断が必要な事項は、推奨案と選択肢を報告する。

## 3. 作業開始時の基準確認

最低限、次を確認する。

- 現在のbranchとremote
- local branchとremote branchの差
- 作業ツリーとstage済みファイル
- ユーザーの未コミット変更
- submoduleの状態
- 現在のHugoバージョンとビルド
- 現在の自動テスト
- 関連するPowerShell、Python、GitHub Actionsの構成
- 対象Phaseが利用する外部サービスの設定有無
- 変更前の公開、プレビュー、校正、通知などの安全ガード

ユーザーの既存変更は、内容を確認して作業対象から除外する。変更、破棄、上書き、stash、reset、checkoutによる巻き戻しを勝手に行わない。

基準確認の結果は対象Phaseの実装報告へ記録する。

## 4. 保護対象

次は、Phase固有の明示依頼がない限り変更しない。

- Obsidian原稿の `index.md`
- 記事ごとの `images/`
- ブログ以外の個人メモ
- 既存公開記事
- 独立した `my-blog`
- `my-blog` の公開操作
- PaperMod submodule内部
- Git履歴上のユーザー変更
- 外部サービスのアカウント、Secret、Webhook、設定

`review-report.md` はObsidian記事フォルダ内だけで扱い、Hugo同期、commit、GitHub Actions artifact、生成サイト、公開物へ含めない。

削除、移動、上書き、再圧縮、履歴書換えなど回復しにくい操作が必要な場合は、対象と理由を示して明示承認を得る。

## 5. 秘密情報と個人情報

次をリポジトリ、ログ、テストデータ、通知、生成物、チャットへ表示または保存しない。

- APIキー
- GitHub token
- Discord Webhook URL
- Authorizationヘッダー
- 認証Cookie
- 秘密鍵
- `.env` の値
- 解析IDなど公開を意図しない識別子
- 非公開のメールアドレスと個人情報

秘密情報を検出した場合は、値を表示せず、種類と安全な場所情報だけを報告して停止する。

Secretが未設定の場合は、Secret名だけを示す。架空の値や、本物に見える固定文字列を作らない。テスト用の値は明らかな無効値を実行時に組み立て、実サービスへ送らない。

外部サービスへ送る情報は許可リストで限定し、送信前に人が確認できるdry-runまたは一覧表示を用意する。リポジトリ全体、Obsidian全体、別記事、個人メモ、画像本体、過去レポートを一括送信しない。

## 6. 外部サービスと承認

ローカルの読み取り、実装、fake・stubテスト、資料更新までは、Phase固有の依頼範囲で進める。

次は、ユーザーがその作業を明示的に承認した場合だけ実施する。

- APIやWebhookへの実通信
- Discord、SNS、メールなどへの実送信
- GitHub Secretsや外部サービス設定の追加、更新、削除
- Obsidianショートカットの変更
- commit
- push
- GitHub Pagesなどへの公開反映
- 外部アカウントの作成や変更

承認前に、変更内容、送信先、送信件数、データ範囲、テスト結果、失敗時の影響を報告する。以前の承認を別サービス、別送信先、別Phaseへ拡大解釈しない。

外部サービスの仕様、料金、無料枠、モデル、API、GitHub Actions、セキュリティ要件など変更され得る情報は、実装時に公式一次資料で確認する。

## 7. 安全な実装

- 読み取り対象と書き込み対象を分離する。
- 書き込みファイルを必要最小限に限定する。
- 完成前の出力は同じ保存先の一時ファイルへ書き、検査成功後に置き換える。
- 失敗時に途中ファイルを残さず、既存の正常ファイルを壊さない。
- 同じ入力での再実行が無用な差分や重複処理を作らないようにする。
- 外部入力、AI出力、記事slug、commitメッセージ、URLをコマンドとして実行しない。
- シェル、JSON、YAML、Markdown、URLへ値を渡すときは、文字列連結だけに頼らず安全にエンコードする。
- タイムアウト、限定的な再試行、エラー処理を設ける。
- エラーへSecret、入力全文、応答全文、生のHTTPヘッダーを含めない。
- サードパーティ依存を追加する場合は、必要性、供給元、バージョン固定、更新方針を確認する。
- 既存の安全ガードを無効化して作業を通さない。

警告と停止条件は区別する。改善提案や未設定の任意機能は原則として警告とし、データ破損、秘密情報、公開条件違反、検査失敗、安全に解析できない入力は停止する。詳細は現在の仕様と対象Phaseの要件を優先する。

## 8. Gitと公開

- 公開承認前にcommit・pushしない。
- stage済みの別変更がある場合は停止する。
- commit前に対象ファイル一覧を確認し、対象Phase以外を含めない。
- 記事公開では、既存仕様どおり対象記事だけをcommitする。
- `review-report.md`、Secret、`.env`、一時ファイル、キャッシュをcommitしない。
- ユーザーの変更を自動的に巻き戻さない。
- 履歴書換え、強制push、破壊的なGit操作は、明示依頼と影響確認なしに行わない。
- push後は対応commit、GitHub Actions、公開URLを確認する。
- GitHub Actionsや公開に失敗した場合は、原因と安全な再実行方法を報告する。公開済み記事を自動削除・revertしない。

## 9. テスト

変更前に現在のテストとHugoビルドを実行し、変更後に同じ基準を再確認する。

各Phaseでは最低限、次を確認する。

- 新機能の正常系
- 入力不正、欠落、通信失敗、保存失敗などの異常系
- 秘密情報の値をログへ出さないこと
- 失敗時に既存ファイルを壊さないこと
- 再実行時の差分と重複処理
- 既存Phaseの回帰テスト
- UTF-8の日本語
- PowerShellとPythonの実行環境
- ローカルHugoビルド
- GitHub Actions相当のHugoビルド
- `review-report.md` が同期・公開されないこと
- Obsidianショートカットと `my-blog` が維持されること

外部AI、Discord、SNS、メール、Webhookなどのテストはfake、stub、ローカルHTTPサーバーを使い、承認前に実サービスを呼ばない。本番公開を故意に失敗させてテストしない。

テスト数だけで完了とせず、対象Phaseの停止条件と安全条件を直接検証する。

## 10. Phase境界

- 対象Phaseの目的達成に必要な範囲だけ実装する。
- 後続Phaseの機能は、将来必要になる構造を壊さない範囲の準備に留める。
- 後続Phaseの外部接続、通知、自動生成、SNS、分析、バックアップを先行して有効化しない。
- 保留事項は未実装のまま明記し、仮のSecretや外部設定で埋めない。

## 11. 資料の同期

方針、現在状態、操作方法、確定値を変更した場合は、影響する次の資料を同期する。

- `docs/blog_automation_spec.md`
- `docs/roadmap.md`
- `data/editorial/strategy.yaml`
- `docs/game-blog-operation-plan.html`
- `docs/publishing-workflow.md`
- 対象Phaseの実装報告
- 必要に応じて `docs/README.md`

共通安全ルールを変えた場合は、`AGENTS.md` と本書の役割が重複・矛盾していないことを確認する。

過去の監査・実装報告は当時の状態を残す。現在のキー、モデル、状態へ一括置換せず、明確な誤記または追補が必要な場合だけ、その理由が分かる形で更新する。

Phase完了時は `docs/phase-<番号>-implementation-report.md` を作成し、少なくとも次を記録する。

- 変更前の基準
- 実装内容
- 安全設計
- 警告と停止条件
- テスト結果
- 外部接続と外部変更
- 決定事項
- 保留・未実装事項
- commit、push、Actions、公開の状態
- 次Phaseへ進めるか

## 12. 完了報告

非エンジニアにも判断できる言葉で、結果を先に報告する。

最低限、次を含める。

- 実装した内容
- 既存機能への影響
- データと秘密情報を守る仕組み
- 警告と停止条件
- テスト結果
- 未実装・保留事項
- ユーザー判断が必要な事項
- 外部サービスへ実際に行った操作
- commit・push・公開の状態
- 次Phaseへ進める状態か

技術的な警告は、現在の動作への影響と、いつ対応が必要かを分けて説明する。

## 13. Phaseプロンプトに残す内容

各Phaseのプロンプトでは、本書の全文を繰り返さず、次だけを追加する。

- 対象Phaseと目的
- Phase固有の確認資料
- 現在までに確認済みの状態
- Phase固有の実装範囲
- 実装前にユーザー判断が必要な事項
- Phase固有の通知、外部サービス、データ範囲
- Phase固有の警告と停止条件
- Phase固有のテスト
- 作成する実装報告
- 外部接続、commit、pushの承認範囲
