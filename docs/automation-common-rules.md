# 管理画面再構築の共通ルール

## 1. 現在の目的

Hugoのブログ本体と安全な公開基盤を維持しながら、Obsidian、Discord、個別コマンドに分散した日常操作をローカル管理画面へ集約する。

現在の最優先は記事管理である。アクセス解析、SNS自動化、AI編集部、リリース・セール情報は、記事投稿の基本機能が完成するまで実装を保留する。

## 2. 判断の優先順位

1. 現在のコードとテスト
2. `docs/publishing-workflow.md`
3. `docs/blog_automation_spec.md`
4. `docs/roadmap.md`
5. `config/editorial/strategy.yaml`

`archive/` は過去の記録であり、現行仕様の根拠にしない。

## 3. 必ず守る安全策

- ユーザーの未コミット変更を変更、破棄、上書き、巻き戻ししない。
- 記事本文、画像、個人メモを、明示された処理以外で変更、移動、削除しない。
- 既存公開記事を自動的に書き換えない。
- `review-report.md` を公開、同期、commit対象へ含めない。
- 独立した `my-blog` とPaperMod submoduleを変更しない。
- APIキー、Webhook URL、token、Cookie、認証情報、個人情報を表示、保存、commitしない。
- AI出力や外部入力をコマンドとして実行しない。
- テストから実AI、SNS、Discord等を呼ばない。
- commit、push、公開、外部サービス変更は、ユーザーの明示承認後だけ行う。予約公開は、検査結果と日時を表示した確認画面の「この日時で予約する」を、対象記事と指定時刻に限った事前の明示承認として扱う。

## 4. 管理画面の原則

- 管理画面は初期版ではPC内の `localhost` だけで動かす。
- 記事本文と画像は通常のファイルとして保持し、特定アプリだけでしか読めない形式に閉じ込めない。
- SQLiteは状態、予定、履歴などの補助情報に限定する。
- 保存は一時ファイルと原子的置換を使い、失敗時に正常な原稿を壊さない。
- 削除は初期版では行わず、アーカイブまたはごみ箱相当の復元可能な操作にする。
- 公開は、検査結果と対象記事を表示した後の明示承認を必要とする。
- 管理画面の操作から、記事以外の変更を同じcommitへ混ぜない。

## 5. 保留機能

`archive/` に退避したコードとワークフローは実行対象に戻さない。再利用時は、管理画面の共通データ構造と承認フローへ接続し、fake・stubテストを作り直す。

## 6. バックアップ

毎日と月次の暗号化バックアップは、記事を守る独立した安全機能として継続する。Discordエラー通知は停止し、失敗はローカルの非公開状態記録へ残す。復元先に稼働中の原稿フォルダを直接指定しない。

## 7. 作業開始と完了確認

変更前後に次を確認する。

- branch、remote、作業ツリー、stage、submodule
- ユーザーの既存変更
- 関連テストと全回帰テスト
- Hugo本番相当ビルド
- Git差分と秘密情報
- 保留ワークフローが通常実行場所へ戻っていないこと
- 外部変更、commit、push、公開の有無

## 8. 資料同期

方針、操作、確定値を変えた場合は、README、仕様、roadmap、操作手順、strategyを同時に更新する。過去資料は `archive/` に残し、現行値へ書き換えない。
